# Architecture

## Boundary

Canonical state lives in `framework-core`. The UI cannot mutate it directly.

```text
React canvas ── Tauri command adapter ──┐
                                       │ typed operations and views
AI agents/scripts ── MCP adapter ──────┤
                                       ▼
                                framework-core
    ├── Document and stable IDs
    ├── Formula parser and dependency graph
    ├── Evaluation and summaries
    ├── Undo/redo history
    └── JSON persistence
```

The React interface runs inside Tauri and reaches the core only through the desktop command adapter. There is deliberately no browser-only fallback: the former in-memory preview duplicated operation and evaluation semantics in TypeScript and was removed rather than maintained as a second engine.

The MCP adapter is also intentionally thin. It translates discoverable, human-oriented arguments such as a table name and 1-based row number into the same stable IDs and typed `Operation` values used by the desktop. It does not automate screen coordinates or implement a second formula engine.

Formula text uses Polars expression syntax with exact backtick references in place of `pl.col(...)`. The parser resolves data references to stable IDs and preserves ordinary operator precedence, lists, keyword arguments, method chains, and namespaces. The compiler then creates native Rust Polars `Expr` objects; it does not interpret Python or evaluate arbitrary code. A canonical catalog describes the root functions and methods exposed to UI and MCP autocomplete. The supported surface is indexed in [formula-function-catalog.md](formula-function-catalog.md).

Categorical columns persist an ordered set of allowed string values in the document model. The core validates mutations before publishing them, while Polars currently receives the column as a string series so existing formulas and joins remain compatible. A future canvas Series object will represent reusable one-dimensional Polars values separately from scalar text and number constants.

## Identity

Standalone values, tables, rows, views, summaries, and documents receive UUIDs. Columns receive an immutable readable ID shaped like `amount~k7m3q2`: a slug from their creation name plus a short random suffix. The editable column name and, for imports, the physical source-field binding are separate. An ordinary table cell is identified by `(table_id, row_id, column_id)` and does not receive another global ID.

Names are aliases. When a formula is accepted, its identifiers are resolved to IDs and stored in an expression tree. Display text is rendered from the current names, which is why renaming does not break references.

## Formula validation

Column formulas form a dependency graph. Every formula mutation reconstructs and checks that graph. A cycle is rejected and the mutation is rolled back before it enters history.

Explicit recurrence will be a separate future computation type with declared ordering and an initial value. It will not be represented as a circular ordinary formula.

## Operations and history

The desktop and automation boundaries accept tagged operations such as `SetValue`, `AddRow`, `DeleteRow`, `SetCell`, `AddColumn`, `DeleteColumn`, `DeleteObject`, `SetColumnType`, `RenameColumn`, `AddComputedColumn`, and `SetCellOverride`. Undo is a stack of *inverse operations*, not document snapshots. Every applied operation has its inverse computed in `invert.rs` against the state before it lands — the prior value can only be read while it still exists — and undo applies that inverse forward like any other edit. Most operations invert to themselves replayed with the values they replaced; where the forward edit destroyed something no operation can describe (a dropped column also drops its summaries and cell overrides; the tab operations add and remove whole cards) the inverse restores the affected subtree through `RestoreTable`, `RestoreObject`, or `RestoreViews`. Those carry one table, one object, or the view list — never the document, which is what makes this cheaper than the snapshots it replaced as well as more correct. Two consequences: a remote event no longer voids the undo stack (snapshot history had to clear it, since restoring one could erase the remote edit wholesale), and undo reverts one edit rather than every difference between two snapshots. An inverse that no longer applies is dropped rather than retried, and only that entry is lost. Document revisions remain monotonic across apply, undo, and redo so programmatic clients can detect stale writes. Deletion is dependency-safe: a value or column referenced by another formula cannot be removed until that dependency is changed, while summaries attached to a deleted unreferenced column are removed with it.

Before application, a user-facing `Operation` is prepared as a `ReplicatedOperation`. Preparation assigns every object, view, row, column, and summary ID at the originating replica and resolves formula text into its stable-ID expression tree. `OperationEvent` wraps that prepared mutation with a document ID, writer/sequence identity, causal version vector, and event-format version. Replaying the serialized event therefore does not generate different IDs or reinterpret renamed formula references.

The desktop and `.fw` MCP adapter publish each accepted mutation as one immutable `.json` file under `events/<writer-id>/<sequence>.json`. The desktop writer ID is generated once per installation and retained in application data; an MCP server process owns a fresh writer ID for its session. The `.fw` snapshot records the applied version vector, so rescans skip events already represented by the snapshot. The desktop rescans in the background and pushes merged documents into the open UI, while MCP rescans before each request. Both leave sequence gaps pending until sync supplies the missing files. This is shared-drive event exchange, not yet a live peer session or a complete CRDT conflict policy; concurrent structural conflicts still need explicit reducer semantics.

## Persistence

The native app saves an ordinary, versioned `.fw` file that can be associated with the installed application on Windows, macOS, and Linux. It is deliberately a normal file rather than a macOS directory package. The file currently contains an inspectable JSON snapshot; legacy bare JSON documents remain readable.

Imported data has two deliberately separate concepts. A `DataArtifact` is the immutable snapshot owned by the document: imports are normalized to Parquet, identified by a SHA-256 content hash, and stored under the document's companion data directory. An optional `ConnectorRecipe` records how that snapshot was obtained, such as the original file path. Computation reads the artifact, never the connector, so reopening a document is deterministic even if the source file changes or disappears. Refresh explicitly reruns the connector into a new artifact and publishes a typed artifact-swap operation; it never mutates the existing snapshot in place. `SetTableSource` is the same swap with the connector replaced too, which is how a table follows a file that moved or advances to the next period's export. Replacement reconciles fields through their physical source bindings. Surviving fields keep their column IDs, additions receive new IDs, unused deletions disappear, and referenced deletions retain their identity so downstream evaluation fails with the missing source field named explicitly. An editable display rename never changes which Parquet or SQL field is read.

Collaboration and artifact data use a companion `.framework/<document-id>/` directory beside the `.fw` file, with separate `data`, `events`, `checkpoints`, and `sessions` directories. The document ID keeps this path stable when the visible file is renamed. Save As copies owned artifacts into the new companion directory and rewrites their locations before saving. Event files are writer-owned and immutable so shared-drive clients synchronize independent files rather than contending over one append-only file. A future local SQLite database belongs in application data as a cache and WAL; a live SQLite database must not be shared directly through OneDrive, Google Drive, Dropbox, or a network filesystem.

## Large table viewport

Table cards persist their width and height as typed `ResizeView` operations. Rows scroll inside the card, while the header remains visible. The React table uses a fixed-height virtual window: only the visible rows and a small overscan buffer are mounted, with spacer rows preserving the full scroll range. DOM and input-rendering cost therefore stays bounded as the row count grows. The spacer surface is capped at eight million pixels and maps that physical range onto logical row offsets, avoiding browser layout-height limits even when a future paged source reports a billion rows.

Each canvas view is a spatial window containing tabs, and **a tab is another rendering of data the card already shows** — `CanvasView.tab_object_ids` lists them in strip order and `object_id` is the selected one, so "which tab is active" and "what does this card show" are the same question rather than two fields that can disagree. Tables and plots both qualify. Adding a table tab creates a pass-through child table (`BranchTable`), which is cheap because nothing computes until someone reads it; adding a plot tab is `AddPlot` with a `view_id`. Both resolve to the same `AddTab` replicated operation, because both are the same edit to the strip. Closing a tab deletes the object it is, and renaming one renames the object. Tabs can move between windows (`MoveTab`) or detach into a new window (`DetachTab`); moving the final tab moves the window rather than orphaning the object.

One rule governs what may join a strip, in `Document::validate_tab_target`: a tab is the card's own object, a single-source derived table with no join, or a plot whose source table the card already shows. Everything on a card therefore traces back to the same data, so switching tabs changes the presentation and never the subject. A joined table has two parents and so no unambiguous home. The tab strip is rendered by `CanvasObject`, above whichever body the selected tab calls for — it belongs to the card, not to the table inside it.

Windows can be arranged with `TidyLayout`, which lays them out in columns by lineage depth: a table sits one column right of the furthest-left thing it reads, and a plot one column right of the table it draws. Within a column, children stack under the parent they came from. The arrangement is a pure function of the document (`Document::tidy_layout`), computed while preparing so the operation carries resolved positions rather than an instruction — a replica reproduces the same canvas, and tidying twice is a no-op rather than a slow drift.

Every table carries two layers. Its **wrangle chain** (`TableObject.steps`) is what the table *is*: lineage, and everything derived from it reads those steps. Its **display layer** (`TableObject.display`) is how it is *shown*: a trailing filter and sort that apply to this table's own reads and never propagate. Both are the same `TableStep` type run through the same evaluator, so a display filter and a wrangle filter are one code path with one null convention. The entire propagation rule is that every recursive call in `materialize_table_lazy` asks for `Layer::Data`; the display layer is only ever added at the top. Two tabs filter independently because they are two tables, not because a parallel state machine keeps their filters apart.

Selection is by cell range, not by row. Dragging extends a rectangle from the pressed cell; shift-click extends from the anchor; clicking a column header or a row's index selects that whole line of the table. The last of those cannot be expressed as an anchor and a focus cell — an imported table holds only the scrolled-to window on the client, so "every row of this column" has no far corner to point at — so it rides on the focus as a `span` and is resolved separately: against the rendered window when painting the highlight, against the table's real row count when copying. The span-to-axis mapping lives in `gridSpan.ts` because the two orientations disagree about which screen axis a table row runs along.

Copy, cut, and paste all act on that selection. Copy writes tab-separated text, optionally with a header row (a remembered preference, and both are offered in the context menu); a selection reaching past the loaded rows is fetched a page at a time and confirmed first past 200k cells. Pasting into an *empty* table replaces it outright — text goes to the core and is parsed by the same Polars reader a file import uses, so a pasted column of dates becomes a date column exactly as an imported one would. Pasting anywhere else writes from the anchor and grows the table when the block overruns the last row (`PasteCells`), but never adds columns: widening a table is a schema change, and one made by accident is not a paste. Creating a table therefore produces an empty 2×2 rather than a dialog to paste into — the grid is the better text box.

A chain is walked one step at a time, and every step is parsed against the schema at its own position — which is what lets a step read a column an earlier one produced, and why a calculated column after a summarize needs no special stage. `walk_pipeline` records that schema at every position and hands it back, so the same walk answers two questions: what to save, and what the editor's *unsaved* draft would produce. `preview_table_pipeline` is the second one. It costs no scan, because `collect_schema()` resolves names and types from the plan without touching a row, and a draft that stops at a step it cannot work out is an ordinary answer — the schemas before it hold and the offending step is named, so it can be fixed or deleted rather than only failing on save.

Rows at a step are the other half, and they cost what the schema does not: `sample_table_step` walks to a step, keeps the plan, and runs `.limit(n + 1)` on it. The limit pushes into the plan, so a step over four million rows reads what it needs rather than the lot, and the extra row answers "there is more below" without a count — counting is the scan a sample exists to avoid. Because it is real work, the editor fetches it *once*: opening a step's preview loads it without being asked, and editing the chain afterwards marks it out of date rather than refetching. Re-running a query on every keystroke is how a preview becomes something people turn off.

That freeness has a boundary, and the pivot step settled how it is held. A pivot names its output columns after the *values* in a column, so its schema is not a property of the plan — but rather than making schema answers sometimes cost a scan, the pivot looks at the data exactly once, when the step is written: `parse_pipeline_step` reads the distinct values of the names column and bakes one output per value into the step, the way a join bakes its outputs. From then on the schema is resolvable from the plan again, saves are the schema contract they always were, and a new value appearing upstream waits for a re-save instead of silently reshaping every table downstream. The cost is one bounded scan per save or preview of a chain holding a pivot. Unnesting something whose fields are not known ahead of time will face the same choice; a step's schema stays a struct rather than a bare column list so a step that instead chooses to be data-dependent can say so.

Sort keys are `{ columnId, descending }` and nulls always sort last regardless of direction, in the wrangle chain and the display layer alike. Filtering happens before ordering. A display filter or sort can be turned into lineage with `PromoteDisplayToSteps`, which moves it into the wrangle chain — the one-way door, taken deliberately.

The table UI separates frequent selection-aware commands into a contextual ribbon and deeper configuration into Selection, Format, Rules, Table, and View inspector sections. Direct formatting is persisted on each table as sparse style entries in its display layer targeting stable table, row, column, or cell identities. Effective styles cascade from table to column to row to cell, so sorting, filtering, and changing orientation do not move a one-off format onto different data. Conditional formatting is view-local style queries compiled into hidden Polars expressions over the rendered result. Every rule on a frame becomes one aliased column in a single `with_columns`, so the rules are optimized together and each source column is read once. Those columns sit above the page slice rather than over the page: a rule may ask something of the whole column — an average to compare against, the ends of a ramp — and an answer computed over the visible thousand rows would be a different answer on every page. A read that already materialized every row runs them over that and slices the answers; the paged read puts them in the plan and lets Polars push the slice through the elementwise ones. Those columns are read off the collected result as style and dropped there: they never enter the schema, never become downstream analytical data, and never mutate a source column.

What a rule returns decides how it is read, and the type is checked when the rule is set rather than chosen from a menu: a boolean picks the rows it answers true for, text sorts rows into named cases with an optional catch-all, and a number is read as a position between 0 and 1 on a ramp of two or three colors. The rule carries no numbers: where a row lands is the formula's own answer, which `normalize()` computes — the column's own `min` and `max` by default, two given numbers positionally, or `center=` for a ramp symmetric about a number that matters. Those aggregates ride the same path as any other in a rule, so they see the whole column rather than the visible page, and every variation of a scale is an edit to the formula rather than a control on the rule: pinning ends, flattening outliers with `clip`, taking a log first, or standing another column's value in for the real one with a `when` chain. Chained `when/then/otherwise` is the same move for the text reading, collapsing several columns into the one label a rule paints. A case list is not typed out by hand: the panel asks the engine for the distinct values the rule's formula produces over the frame's display layer, commonest first with ties broken on the label so every caller gets the same list, and hands each one a color from a fixed palette. That is a read rather than an operation — the colors are chosen on the interface side, and what the document stores is the plain mapping somebody ended up with, every entry of it editable and removable afterwards. The core resolves each answer into a `FrameCellStyle` and publishes it against a stable row ID — on `ComputedFrame` for a table that holds its rows, on the page for one that does not, since a page is the only place a paged table's rows exist. Rules apply property by property over direct formatting, in rule order, so a rule replaces only the attributes it sets and later rules win. A rule that fails to run reports itself by ID and is skipped; the other rules and the table still render.

A style stores one color per property, always the light-mode value, and dark mode is derived rather than stored beside it — the alternative is a document carrying two answers for every color and a person keeping them in agreement. The derivation is a reflection in OKLCH: same hue, same chroma, and a lightness as far from the dark paper as the original sat from the light one. That preserves what a color was chosen for, since contrast against the paper is what makes a highlight loud or quiet, and it holds a ramp's order because it is monotonic in lightness. Reflection is its own inverse, so a color picked while the window is dark is written down reflected and comes back looking as it was picked; it is applied at the render boundary as a CSS `light-dark()` pair, which leaves the choice to the engine that already knows the theme and needs no subscription or re-render when the system flips. The engine is unaffected: it mixes ramp ends in the stored light-mode hex, and the mixture reflects like any other color.

Imported CSV and TSV files are converted to content-addressed Parquet artifacts in streaming batches with 65,536-row groups; Parquet imports are adopted into the same artifact store. Artifact-backed tables expose metadata through `DocumentView` and fetch rows through a separate page query. That query keeps direct and derived Polars plans lazy, applies the display layer, slices to the requested range, and only then collects the bounded result. The browser virtualizer maps its visible range onto those backend pages, so neither the UI boundary nor an ordinary page request materializes the complete dataset.

This is the out-of-core foundation, not the end of the large-data work. Computing an exact filtered or derived row count can still scan an artifact, and exports and some global operations still need streaming implementations. File refresh is manual and does not yet offer schema migration, scheduled refresh, progress reporting, or artifact garbage collection. Operation deltas, checkpoints, query caching, and explicit resource limits remain later milestones.

## Automation and collaboration boundary

`framework-mcp` exposes the core through local MCP over standard input/output. Read tools return structured JSON and stable IDs. Write tools accept an optional `expectedRevision`, persist immediately, and are annotated as mutating so capable clients can apply their normal approval policy.

The desktop and MCP adapter now exchange operation events with other replicas through the companion shared-drive directory. A single-owner local service remains the target for immediate subscriptions, transaction grouping, undo semantics, and coordinated writes from several adapters on one machine:

```text
Desktop UI ─────┐
Human scripts ──┼── command/query protocol ── framework service ── storage
AI/MCP clients ─┘                              ├── operation log
                                               └── change subscriptions
```

That service will serialize writes, provide subscriptions, and eventually host conflict resolution. MCP, CLI/SDK, and desktop transport should remain adapters over one command/query contract rather than independent implementations.

## Polars boundary

Polars 0.55 is the formula execution engine. Raw table columns become a DataFrame and calculated columns compile into one lazy query. Independent expressions are batched into the same `with_columns` call; references to newly calculated columns create subsequent topological layers. The complete plan is collected once, allowing Polars to optimize across the query while preserving dependency semantics. This gives formulas native Polars typing and null semantics and enables aggregations, shifts, grouped windows, and rolling expressions without maintaining a second evaluator.

FrameWork still owns document identity, dependency-cycle checks, operation history, display formatting, and the safe parser/compiler boundary. Only explicitly compiled expression methods are available; Python execution, UDFs, plugins, file I/O, and arbitrary callbacks are outside the formula surface. Derived-table operations such as joins, filtering, grouping, sorting, and reshaping will use Polars `LazyFrame` plans rather than calculated-column expressions.

Aggregate and group-by results are now first-class derived table objects. A derived table stores its source table ID, stable output-column IDs, grouping expressions, aggregate expressions, and ordering policy. Total aggregation is the same plan with no grouping keys. Materialization recursively evaluates upstream tables, so a source may branch into several results and any result may feed another derived table. Canvas views render lineage cords from these dependencies, while result cells remain read-only and output aliases can change without changing column identity. Every table view also persists an independent collapsed state.

Selecting a derived table edits that table's existing transformation against its actual source rather than implicitly creating a second summary from the result. Transformation updates preserve retained output-column IDs, add stable IDs for new outputs, and reject removal when a downstream derivation still references the output. Group and custom aggregate expressions share the calculated-column formula editor and exact-backtick autocomplete.

Legacy summary footers remain deserializable for existing documents, but the UI no longer creates or renders them. New totals and grouped summaries use derived tables.

Derived tables also support a non-aggregate projection mode. Creating a table from another table produces a live identity projection with new stable output-column IDs and a lineage edge. Its transformation can filter source rows (matching all or any conditions), retain a subset of source columns, apply a stable multi-column sort, or switch to group-and-aggregate output. Filters execute before that table's projection or aggregation, and sorting executes afterward. To filter an aggregate result, create a generic child from that result; the canvas lineage therefore makes the before/after relationship explicit. All stages compile into the same recursive Polars lazy plan, so edits to an upstream table refresh every descendant branch.

Joins are also first-class derived tables. A join stores two parent table IDs, exact stable-ID key mappings, a policy (left, inner, anti, or semi), and stable output-column mappings back to either input. For left and inner joins the lookup-side key must be an enforced unique-key constraint; every accepted mutation revalidates those constraints, so duplicate lookup rows cannot silently expand a result, and Polars executes them with many-to-one validation. Anti and semi joins keep only primary-side rows and columns: they test lookup-key membership, so duplicate lookup keys cannot expand their result, the unique-key requirement is relaxed for those two policies, and validation rejects lookup-side output mappings. Null keys do not match under any policy. Joined results remain read-only, may feed later derivations, and render one lineage cord from each parent.
